Dispute & Cancellation Flow
How disputes are raised, resolved, and how cancellations work
⚠️
Phase 1: Dispute Raised
Household can dispute from multiple task states
1
Dispute Trigger
Household raises a dispute with a reason (10–500 chars). Can be raised from: ACCEPTED, SCHEDULED, IN_PROGRESS, COMPLETED, or VERIFIED.
PATCH /api/tasks/[id]/escrow (action: "dispute")
Immediate Effects
Task → DISPUTED
Escrow → DISPUTED (if escrow exists)
Active booking → cancelled (assigned/accepted/in_progress → cancelled)
HouseholdCategoryAutonomy: promotionPaused = true
Both household & vendor notified (DISPUTE_RAISED)
↓3 Resolution Paths
⚖️
Phase 2: Dispute Resolution
Three possible outcomes for a disputed task
✅ Path A: Household Resolves
POST /api/tasks/[id]/resolve-dispute
Escrow: DISPUTED → HELD
Task: DISPUTED → COMPLETED
promotionPaused = false
→ Can re-verify & release escrow
🛡️ Path B: Ops Dismisses
PATCH /api/ops/escrow/[id] (resolve_dismiss)
ADMIN/COORDINATOR role required
Escrow: DISPUTED → HELD
Task: DISPUTED → COMPLETED
Audit log created
💰 Path C: Ops Refunds
PATCH /api/ops/escrow/[id] (resolve_refund)
ADMIN/COORDINATOR role required
Escrow: DISPUTED → REFUNDED
Task stays DISPUTED (no change)
promotionPaused = false (no penalty)
↓Separate from Disputes
🚫
Phase 3: Cancellation
Three distinct cancellation scenarios
2
Ops Cancels Booking + Task ADMIN only
The ONLY way to reach TaskStatus.CANCELLED from non-predicted tasks. ADMIN role required. Works from any non-terminal state.
PATCH /api/ops/bookings/[id] (action: "cancel")
Effects
Booking → cancelled
Task → CANCELLED
cancelReason saved
Audit log created
3
Household Cancels Predicted Task
Only for PREDICTED tasks before lockAt. Sets cancelledAt + cancelReason. Task status stays PREDICTED (preserved for analytics). Excluded from task lists.
POST /api/tasks/[id]/cancel-predictive
Soft-Delete Pattern
Status remains PREDICTED (not changed to CANCELLED)
cancelledAt IS NOT NULL marks it as deleted
4
Vendor Rejection / Timeout Effective Cancel
Vendor rejects or 15-min timeout expires. Booking → cancelled. Task stays in MATCHING state (not cancelled). Auto-re-routes to next vendor.
PATCH .../bookings/[id] (reject) | POST /api/tasks/timeout-check
Auto-Re-Routing Logic
matchAttempts < 5 → try next vendor (new booking created)
matchAttempts ≥ 5 or no vendors → needsOpsIntervention: true
📊
Escrow State Machine Summary
4 possible escrow states
HELD
Created on vendor accept. Awaiting verification or dispute.
→ RELEASED or DISPUTED
RELEASED
After household/ops release. Vendor gets paid (minus 10% commission).
Terminal state
DISPUTED
Household raises dispute. Awaiting ops/household resolution.
→ HELD or REFUNDED
REFUNDED
Ops upholds dispute. Full refund to household. Ledger state change only.
Terminal state
Dispute / Cancel
Warning / Soft Cancel
Resolution
Info / Re-routing
